## 0.1 项目一句话定义

> **一套移植到任意 ARM Cortex-M（M0+/M3/M4）数字电源固件里的软件频率响应分析库，配一个 PyQt5 上位机（单窗口双 Tab：测量 + 补偿器），在真实硬件上测出环路 Bode 图并读 PM/GM。**

**交付件**：`sfra_core` / `sfra_proto` / `sfra_port` 三个固件文件 + 上位机 + SOP。不碰用户现有固件工程。

---

## 0.2 借鉴原则（最高优先级）

> **不重复造轮子。优先级：TI SPRUHZ5A → libsfra → 自写。**

| 层 | 来源 | 抄什么 |
|---|---|---|
| 测量定义 | **TI** | Ref 注入法、`GH = Y/(Inj−Y)`、per-unit 全链路、Plant/GH 两套数组、ISR 内 4 次乘加、background 换频点状态机 |
| C 实现技巧 | **libsfra** | `fast_sin` 1/4 周期查表+线性插值、整周期取整反算角步进、`filter_rc.h`（L2 自测被控对象）、int64 累加器、RAMFUNC 宏 |
| 自写 | 仅两处 | 串口二进制协议（TI 私有不可用、MODBUS 寄存器模型别扭）、PC 上位机（TI 不开源） |

**禁止自造**：幅相计算公式、状态机结构、取点约定。任何与 TI/libsfra 不一致处必须在代码注释里写明原因。

## 0.5 分阶段实施计划（谁先做、做到什么算完）

**一句话答案：先做 PC 端的算法核心（Python），再做固件库（C），最后才做上位机界面。**
理由：算法的正确性只能在"答案已知"的环境里证明；界面只是算法的显示器，算法不确定时做界面等于白做。

### 0.5.1 为什么是这个顺序

| 若反过来做会怎样 | 后果 |
|---|---|
| 先写 C 库、上真机 | 相位反了 / 少一个 2π / f_act 没打通，曲线"看起来像 Bode 图"但不报错 —— 在真机上你无法区分是算法错、接线错、还是功率级非线性 |
| 先做界面 | 界面很快能画出漂亮的曲线，但曲线是假的；之后算法每次改，界面都要跟着改（数据接口一改全崩） |
| 先做协议 | 协议栈是最容易调的部分（串口回环即可），但不知道数据长什么样时定协议会反复推翻 |

算法一旦用 pytest 锁死，后面所有工作都变成"接线"和"搬运"，出错能立刻定位到层。

### 0.5.2 各阶段详解（S0~S7）

> 每阶段都有**明确的完成标志（DoD）**和**验收方式**。DoD 不满足不进下一阶段。

#### S0 · 方案定版（已完成）

- **做什么**：测量定义、协议、分层、验证路线、接入指南全部落到文档，定版为可开发基线。
- **产出**：`00`~`05` 六份文档。
- **DoD**：✅ 公式无自相矛盾；✅ GH 定义与 TI 一致；✅ 每一条设计决策有编号可追溯。

#### S1 · PC 纯算法（L0）— **第一个写代码的阶段**

- **做什么**：
  1. `sim/sfra_sim.py`：逐行移植 `libsfra.c` 的扫频核心（整周期取整、θ 递推、6 个累加器、单/双 pass），**不含 atan2**；
  2. `model/bode_data.py`：累加器原值 → 复数 → mag/phase（**相位约定全项目唯一实现处**）；
  3. `model/analysis.py`：unwrap / fc / PM / GM；
  4. `sim/plants.py`：一阶低通、二阶 LC、数字 PI 闭环；
  5. `tests/`：`test_bode_data.py`、`test_analysis.py`、`test_sfra_sim.py`。
- **不做什么**：不碰串口、不碰界面、不碰 C。
- **DoD**：`pytest` 全绿，且
  - Plant / GH / PM / GM / fc 与 scipy 解析解误差 < 1.5 dB / 3°（Normal 档）；
  - 一阶低通相位 0 → −90°（相位符号锁死）；
  - `test_phase_sign` 必须存在并通过。
- **为什么必须先做**：这是唯一能说"我的算法是对的"的地方。此关不过，后面全是猜。

#### S2 · C 库在 PC 上交叉验证（L1）

- **做什么**：
  1. `sfra_core.c/h`（float32 路径先行，定点路径同一套宏切换）；
  2. `fast_sin` 表（照抄 libsfra）；
  3. gcc 编译成 PC 可执行程序，喂与 Python **完全相同的激励序列**；
  4. 比对**累加器原值**（不是 mag/phase）。
- **DoD**：
  - 浮点路径相对误差 < 1e-5；
  - 定点路径折算误差 < 0.05 dB / 0.3°；
  - 跑 100 万次 inject+monitor 计时，**回写 01/02 文档的开销表**（把"理论估算"换成实测值）。
- **此阶段不涉及任何硬件**。PC 上跑通即证明"Python 和 C 是同一个东西"。

#### S3 · 串口回环 + 协议栈

- **做什么**：
  1. `sfra_proto.c/h` 完整实现（含 3.6 节三个坑：结构体填充、CRC 范围、`AA AA 55` 帧头重同步）；
  2. PC 端 `comm/protocol.py` + `comm/link.py`；
  3. **先用 PC 端的"假 MCU"（回环程序）跑通全链路**：PC 发命令 → 假 MCU 用 S1 的仿真产生数据 → 回传 → PC 解包。
- **DoD**：
  - 帧编解码双向 100% 一致，`test_protocol.py` 全绿；
  - 人为注入错误（坏 CRC、半帧、乱码）时上位机能正确重试/丢弃，不崩；
  - 断电重连后断点续传成功。
- **好处**：协议问题在 PC 上暴露，不用拿真板子试错。

#### S4 · 上位机联调（真链路接通，仍不上真板）

- **做什么**：
  1. `sfra_port.h` 适配层（用户填 4 个函数）+ PC 参考实现 `examples/pc/sfra_port_pc.c`；
  2. **`comm/controller.py`**：把界面接到真链路上——`SweepControllerBase` 定义信号契约，
     `LinkController` 实现 03 §3.4 的完整时序，`SimLinkController` / `SerialLinkController`
     两个后端分别走假 MCU 与真实串口；
  3. 界面首次通过**真实协议路径**（SET_CONFIG→START→轮询→GET_DATA）跑完整扫频，
     而不是调用 `sim/engine.py` 的纯 Python 引擎；
  4. 用 `pyqtSignal` 契约 + `pytest -m e2e` 守住时序，不等真板。
- **DoD**：
  - 离屏（`QT_QPA_PLATFORM=offscreen`）跑通 47 点扫频，`sigDone(True)`，
    `result` 点数与 `SweepConfig.n_points` 相等；
  - 参数非法（幅值越界 / f_stop > f_s/5）时**立刻本地拒绝**，不发给 MCU 空等超时；
  - 用户中止 → ABORT 后立即返回；链路断开 → `sigDone(False, ...)` 且已收到的点不丢；
  - 断点续传：只接受 `chunk.start_idx == 期望 idx` 的段，频率序列严格单调；
  - `sfra_port.h` 的四个函数**必须被假 MCU 走一遍**（`test_port_header.py` 禁止裸 `fwrite`/`getchar`），
    否则上板时才发现 port 层写错。
- **注意**：这一步**不接真板**。目的是把"界面 ↔ 链路"的接缝钉死，
  真板来了只换 `SerialLinkController`，界面一行不改。
  真芯片的数值溢出 / ISR 开销 / 相位符号复验归 **S6**。

> **S4 编号统一说明**：旧版 §0.5.2 正文把 S4 写成"MCU 内部自测（L2）"，
> 而 §0.5.4 进度表写的是"上位机联调"——两套口径。
> 现统一为：**S4 = 上位机联调**，原"MCU 内部自测（L2）"内容整体并入 **S6**，
> 因为 `sfra_port.h` 的四个函数只有在上真板时才被真正调用，它与 L2 自测是同一件事。
> 这也符合 §0.5.3 依赖图里 `S2 → S4` 的箭头。

#### S6 · 真板 L2 自测 + 真实功率级（L3）

**S6a · MCU 内部一阶低通（L2，上真板但还不接功率级）**

- **做什么**：
  1. 填好 `sfra_port.h` 的四个函数（`docs/06` 有逐步指南）；
  2. 用一阶低通替身当被测对象，**不接功率级**；
  3. 上目标板跑完整扫频，用 `tools/selftest_s6a.py` 与解析解逐点比对。
- **已备好的交付件**（真板到手即可用）：
  - `firmware/examples/stm32/sfra_selftest_stm32.c` —— 可烧录的自测主程序，
    含 DWT / GPIO 两套 ISR 计时钩子；
  - `tools/selftest_s6a.py` —— 上位机验证脚本，输出逐点误差表 + PASS/FAIL；
  - `src/tests/test_selftest_s6a.py` —— 判据自身的 10 项自检（防"判据错了"）；
  - `docs/06_S6a上板接入指南.md` —— 从接线到打勾的完整步骤。
- **DoD**：
  - Bode 与解析解误差 < 1 dB / 3°（详见 §6.4 的两条判据）；
  - 示波器 GPIO 翻转法或 DWT 实测 ISR 附加时间：M4F < 10% ISR 周期，M0+ < 20%；
  - 一阶低通相位仍必须 0 → −90°（真机上再验一次符号）；
  - 定点/浮点两条路径在真芯片上都不溢出（int64 最坏情况）。
- **注意**：这一步只验证"数值溢不溢出 + 开销可不可接受 + 相位符号对不对"，不验证功率级。

> **一个必须写下来的数学事实**：固件用 Tustin 离散化，它在 `f_s/5`
> 处比连续域解析解**低 1.26 dB**（相位只差 0.08°）。这是双线性变换的
> 频率轴翘曲，不是缺陷。所以 S6a 的判据分两段：全频段跟**离散域**比
> （0.5 dB/1.5°，真 bug 判据），低频段才跟**连续域**比（1 dB/3°，物理对象）。
> 若只跟连续域比，一个完全正确的固件会被误判 FAIL。
> 这个数字由 `test_tustin_warp_at_nyquist_is_about_1p26db` 锁住。

### 0.5.5 S1 收敛结果（L0 gate 通过）

**判据：与解析解逐点比对，不用"曲线看起来对"当验收。**

| 场景 | 频段 | 幅值误差（中位/最大） | 相位误差（中位/最大） |
|---|---|---|---|
| Plant H（开环） | 100 Hz ~ 20 kHz，100/400 周期 | 0.0000 / 0.0000 dB | 0.0000 / 0.0000° |
| Loop Gain GH（闭环） | 50 Hz ~ 40 kHz，59 点 | 0.0052 / 0.14 dB | 0.014 / 0.19° |

闭环解析基准 `P(z)·C(z)·z⁻¹`，`C(z)=Kp+Ki·Ts/(1−z⁻¹)`。实测 `fc=222.2Hz / PM=111.68° / GM=24.9dB`，解析 `222.2Hz / 111.69° / 24.9dB`。

**S1 期间定位并修复的 6 个算法级缺陷**（全部已固化为回归测试）：

| # | 缺陷 | 症状 | 根因 |
|---|---|---|---|
| A1 | `theta` 在 `inject()` 内推进 | 整条曲线多 `360/data_count` 度相位（高频 −30°） | 相位推进必须在 `monitor()` **之后**（`_advance()`） |
| A2 | 采集窗起点**复位 `theta`** | 20 kHz 出现 +28 dB / +128° | 整周期取整（`dc×step=cycles×2π`）已保证窗内是整数周期，起点相位任意都成立；复位反而在注入波形上造台阶 |
| A3 | 采满 `data_count` 后继续累加 | 窗口尾部多 2~3 个非整周期点 | `monitor()` 采满即停，与固件 DONE 状态一致 |
| A4 | settle 按采集窗比例截断 | 高频 settle 只剩几毫秒，对象未进稳态 | settle 是物理过渡时间，按 `max(20ms, 2T_inj)` 算，与采集窗无关 |
| A5 | 闭环 `sweep()` 少了**一拍计算延迟** | GH 高频相位偏乐观十几度 | 必须 `monitor(u, y_prev)` 之后才 `y_prev = plant(u)` |
| A6 | PI 用增量式 `u += Kp·Δe + Ki·Ts·e` | 高频相位差 70°（20 kHz） | z 域是 `Kp+Ki·Ts·z/(z−1)`，比并行式多一个零点；改用并行式 `u=Kp·e+I` |
| A7 | `loop_confidence` 判据方向反了 | 砍掉准的低频点、放过 `−194dB` 的高频点 | 判"分母 `|Inj−Y|/|Inj|` 过小"，不是"反馈 `|Y|/|Inj|` 过小" |
| A8 | `freq_vector` 未钳奈奎斯特 | `f>f_s` 时多个频点退化成同一 `f_act` | 加 `f_max` 参数，钳到 `f_s/2`（建议 `f_s/2.5` 留余量） |

**关于"每周期采样点数"的结论修正**：早期认为高频误差来自 spc 不足（12 点/周期虚高 15~20 dB）。实测证明 spc = `f_s/f` **与选多少周期无关**，多积周期补不回来；当时的误差真凶是 A1~A4 四条时序缺陷。`MIN_SPC` 仍保留，但只在"周期数过少导致总点数不足"时生效，正常扫频不会触发。

### 0.5.6 S2 收敛结果（L1 gate 通过）

**判据：C 端与 Python 端喂同一段激励，比累加器原值折算后的 dB/度。**
激励序列由 Python 逐拍生成写进文本文件，C 端逐行读入；两边各自独立算几何（cycles / data_count / 角步进），不是把 Python 算好的几何喂给 C。

| 用例 | 累加器相对误差 | 折算 dB | 折算角度 |
|---|---|---|---|
| PLANT Normal | 9.6e-05 | 0.0008 | 0.0012° |
| LOOP Normal | 5.0e-04 | 0.0043 | 0.0161° |
| PLANT Fast | 1.4e-04 | 0.0012 | 0.0048° |
| PLANT Precise | 6.4e-06 | 0.0001 | 0.0003° |
| LOOP Fast | 1.0e-03 | 0.0086 | 0.0277° |
| LOOP Precise | 2.6e-05 | 0.0002 | 0.0006° |
| PLANT Normal Q15 | 2.3e-03 | 0.0196 | 0.0311° |
| LOOP Normal Q15 | 1.9e-03 | 0.0168 | 0.0499° |
| PLANT Precise Q15 | 2.0e-03 | 0.0170 | 0.0013° |
| LOOP Precise Q15 | 1.9e-03 | 0.0168 | 0.0008° |

浮点路径卡 0.01 dB / 0.05°，定点路径卡 DoD 的 0.05 dB / 0.3°。定点实测 0.02 dB / 0.05°，有一个量级余量——Q15 输入的量化噪声下限是 1/(32767·√N) ≈ 3e-8 相对量，折算后约 0.001 dB，所以 0.02 dB 里绝大部分来自"注入幅值被量化到 1/32767 网格"，是物理上就该有的。

**S2 期间定位并修复的 9 个算法级缺陷：**

| # | 缺陷 | 症状 | 根因 / 修法 |
|---|---|---|---|
| A9 | C 端用 float32 弧度累加 `theta` | 100kHz/100Hz 一个频点累加 1e5 次，θ 涨到 6.3e2，float32 ulp 6.1e-5 而步进 6.3e-3，几十拍后相位飘 30°+ | 改 **Q32 归一化相位**（整圈 = 2^32），uint32 自然回绕，零漂移 |
| A10 | `sfra_sincos` 用 `fmod(θ, 2π)` | θ 大时 `θ·N/2π` 丢 6 位有效数字，精度崩塌 | Q32 相位直接取高位当索引，彻底没有浮点取模 |
| A11 | `sfra_sincos` 用 double 插值 | M4F 无硬件 double，展开成 `__aeabi_ui2d/dmul/dadd/d2f`，单次约 500 cycle，100kHz ISR 占 5% | 改**纯整数插值**（int64 乘加 + 一次右移回 Q15），并让 `acc_mac` 也用整数，热路径 0 次软浮点调用 |
| A12 | `gen_script` 每个频点把 phase 归零 | C 端相位跨点连续，脚本每点归零，第 2 点起激励整体错开 | 把 `phase` 提到 `for` 循环外 |
| A13 | float32 / float64 语义不一致 | `freq_step` 写 12 位有效数字再被 C 读成 float32 后差 2e-9，连乘 30 次偏 2e-7；`0.020f×1000.000061f` 在 float32 恰为 20.0 而 double 是 20.0000012，`ceil` 差 1 | `gen_script`/`run_py`/`_pick_cycles` 全部按 float32 复算，写文本统一 `float(np.float32(x)):.9g` |
| A14 | dump 的 LOOP 分支 `y` 带直流 | 写成 `0.5f·r` 把 0.25 直流带进 Y，DFT 残留 `N·DC·Σcosθ` | 与 Python 逐字一致（`y = 0.5·inj`，inj 本身无直流） |
| A15 | Python `inject()` 的 Inj 比 C 多累加 5 拍 | `_collecting` 为真后不判 `acc.n < _total`，C 端判了；Y 停在 data_count 而 Inj 多积 | 加同样的上限判断，LOOP 偏差从 1.41e-3 降到 3.71e-4 |
| A16 | `_acc_ratio` 逐分量归一化 | `a_s ≈ 0` 时被算成 200% 误差 | 改按复振幅模长 `|ΔS|/|S|`，再加 `√N·eps ≈ 1.9e-5` 绝对下限 |
| A17 | 判据用累加器相对误差 | |Inj| 小时相对误差被放大，但折算成相位只有 0.0001° | `compare()` 直接比 dB 与度 |
| A18 | `GET_DATA` 的 NACK 被上位机静默丢弃 | 日志报 `mcu拒绝0x07：INDEX_RANGE`，进度条冻结（实测 57%），界面永不收尾 | `GET_DATA` 不在 `_pending_acks` 队列里，`_on_ack` 末尾的 `if not self._pending_acks: return` 把 NACK 吞掉，`_fetching` 停在非零值 → `_on_poll()` 首句 `if self._fetching > 0: return` 永久命中 → 不再发 STATUS，扫频停摆。修法：`_on_ack` 加 `GET_DATA` 专属分支，**任何错误先无条件清 `_fetching`**；`INDEX_RANGE` 视为正常竞态重试（计数上限 200），其它错误才判失败 |

**"假通过"陷阱（v3.3 补充）**：定点路径第一次跑出 `0.0000 dB / 0.0000°` 的 PASS，实际是 `sfra_dump.c` 把 float 直接传给 `int16` 参数的 `sfra_monitor`，被隐式截成 0/1，C 端累加器全是 0，而旧的 `compare()` 在分母为 0 时 `continue` 跳过。现在 `compare()` 统计跳过数，**任何一个分量为零就判失败**，并在注释里写明理由。

**代码体积与开销（实测，非估算）：**

| 目标 | text | bss | `sfra_inject` | `sfra_monitor` | 热路径软浮点 |
|---|---|---|---|---|---|
| M4F（hard-float） | 2480 B | 2050 B | 101 条 | 103 条 | 0 |
| M0+（float32 路径） | 2404 B | 2050 B | 161 条 | 167 条 | 0 |
| M0+（Q15 定点） | 2440 B | 2050 B | 164 条 | 174 条 | 0 |

bss 里 2050 B 是 `int16` 正弦表（1024+1 点），可用 `tools/gen_sin_table.py` 改成 `const` 放 flash。

PC 上 100 万次 inject+advance+monitor：**浮点 5.8 ns/frame、定点 7.0 ns/frame**（x86-64，-O2）。折算到 100 kHz ISR 分别占 0.06% / 0.07%，200 kHz 占 0.12% / 0.14%。这是上界估计的下界——x86 有超标量乱序，MCU 上还要加访存与流水线停顿，真实周期数必须在目标板上用 `DWT->CYCCNT` 量（S6a DoD）。

**"预计 SNR"为什么必须删掉**：显示一个看起来很精确、实际没有依据的 6 位有效数字，
比不显示更危险——用户会拿它去判断"这个点可不可信"。而真正决定可信度的是
开关纹波、ADC 参考噪声、注入路径失真，这三样在扫频前**一个都测不到**。
现在只报 `1 LSB = 0.024 %pu`、`注入 A %pu = N LSB`、以及"低于 10 LSB 就别信"的经验门槛。

> 编译器不会替你报警。上板请照 `sfra_port.h` 末尾的自检清单逐条勾。

## 0.8 修订记录

- **v4.7（2026-11-24）**：**顶栏合并成一行，「测量 / 补偿器」分页并入顶栏中格**。
  - **问题**：原先顶栏 + 分页条两行各 46px，共 **92px**。而分页条那一行
    除中间 220px 的 Tab 外**全是空白**，等于白扔 46px 高度。
  - **方案选择**：设计稿 `design/sfra-topbar-merge.html` 给了三条路——
    A 完全合并、B 只加底色不省高度、C 合并但 Tab 靠左。用户选 **A**：
    合并 + Tab 依旧居中。
  - **居中怎么做到的（关键，别改坏）**：`QGridLayout` 三列——
    左格（LED+标题）、中格（Tab）、右格（串口组）。
    **左右两格 `columnStretch` 相等（都是 1），中格为 0**。
    这样剩余宽度被左右**平分**，中格的中线自然落在总宽中线上，
    **与左右内容宽度无关**。
    实测 15 档窗口宽度（1120→2560）偏差恒为 **+1.5px**（取整误差）。
    反例：若改成 `QHBoxLayout + addStretch` 对称弹簧，
    左右内容宽度差很多（标题 75px vs 串口组 470px），弹簧容量不同，
    Tab 会被顶走——注入验证实测偏 72~436px。
  - **顶栏高度 46 → 52px**：给 Tab 的 31px 胶囊留垂直余量。
    净省 `46×2 − 52 = 40px`。

- **v4.4（2026-11-24）**：**修掉坑 A18（`GET_DATA` 的 NACK 被静默丢弃）——"卡在 57%"的真凶**。
  - **症状**：日志报 `mcu拒绝0x07：INDEX_RANGE`，进度条冻结（实测 57%），
    界面永不收尾，但画布上已经画到了 2k 终点频率。
    **注意**：上一版曾据"画布已到 2k"判断是"界面完成判据缺陷、扫描本身没卡住"，
    那个结论是**错的**——扫描确实停摆了，只是画布上残留了停摆前已拿到的点。
  - **根因链**（五步，缺一不会发生）：
    1. 上位机某次 `GET_DATA` 请求 `start_idx >= avail` → 固件回 `SFRA_ERR_INDEX`；
    2. 该 NACK 进 `_on_ack`，但 `GET_DATA` **不在 `_pending_acks` 里**
       （那个队列只排 `SET_CONFIG`/`START`）；
    3. `if not self._pending_acks: return` → **NACK 被静默丢弃**；
    4. `_fetching` 停在非零值 → `_on_poll()` 首句
       `if self._fetching > 0: return` **永久命中**；
    5. 上位机再也不发 `STATUS`，扫频彻底停摆，`sigDone` 永不发射。
       MCU 侧可能早已 `DONE`，只是没人问。
  - **根因的上游**：`_available = min(freq_index, n_total)` 与固件
    `avail = (DONE) ? vec_length : point_idx` 语义不对齐。
    `freq_index` 是**"正在采集的索引"**，不是"已完成数"；DONE 后它停住不涨，
    而 `avail` 已变成 `vec_length`——两头都错。

    ① `_on_ack` 加 `GET_DATA` 专属分支，**任何错误先无条件清 `_fetching`**；
