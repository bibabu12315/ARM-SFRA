# 03 通信协议（v3 定版 · 可开发基线）

> 目标：921600 8N1 下可靠、可断点续传、出错能定位。
> v2 变更：**DATA 帧改发累加器原值**（幅相在 PC 算，00 文档 D5/D6）、删 `SET_AMP_LIVE`、删 CL 通道、freq 用实际频率。

---

## 3.1 物理层

| 项 | 取值 |
|---|---|
| 接口 | UART（TTL 3.3V）或 USB-CDC |
| 波特率 | 921600（默认）/ 460800 / 115200（降级） |
| 格式 | 8N1，无流控 |

**带宽核算**：921600 ≈ 92 KB/s。100 频点全量数据（20 B × 100 = 2 KB）传输 < 25 ms，**瓶颈永远是扫频物理耗时，不是串口**。

---

## 3.2 帧格式

```
┌──────┬──────┬──────┬─────────┬───────────────┬─────────┐
│ 0xAA │ 0x55 │ LEN  │ CMD     │ PAYLOAD       │ CRC16   │
│  1B  │  1B  │ 1B   │ 1B      │ LEN-1 字节     │ 2B LSB  │
└──────┴──────┴──────┴─────────┴───────────────┴─────────┘
        LEN = 1 + payload_len       整帧 = 3 + LEN + 2 字节
        CRC16-Modbus，计算范围 = LEN..PAYLOAD 末，共 (1 + LEN) 字节
        初值 0xFFFF，反射多项式 0xA001，CRC 低字节先发
```

**字节偏移速查**（`sfra_proto.c` 与 `protocol.py` 必须逐字对齐）：

| 偏移 | 0..1 | 2 | 3 | 4 .. 3+LEN | 3+LEN, 4+LEN |
|---|---|---|---|---|---|
| 内容 | `AA 55` | LEN | CMD | PAYLOAD | CRC_lo, CRC_hi |

- 双字节帧头 + LEN + CRC 定界，**无转义**（payload 允许出现 0xAA）。
- 应答帧 CMD = 请求 CMD | 0x80；通用应答 `ACK(0x80)` 的 payload 首字节才是被应答的请求号。
  出错 payload = `[err_code(1B), detail(1B)]`。
- 所有整数/float **小端**（ARM 原生）。
- 实测帧长：PING 6 B、ACK 8 B、PING_ACK 10 B、STATUS 16 B、CAPS 22 B、DATA(7 点) 149 B。

## 3.3 命令表（v2）

| CMD | 方向 | 名称 | payload | 说明 |
|---|---|---|---|---|
| `0x01` | PC→MCU | `PING` | — | 探活 |
| `0x81` | MCU→PC | `PING_ACK` | `ver(1) proto(1) cap(u16)` | `cap`：bit0=float, bit1=fixed, bit2=有 Vin/Vout/Iout 回读, bit3=支持 LOOP 单 pass |
| `0x02` | PC→MCU | `GET_CAPS` | — | 读能力与默认参数 |
| `0x82` | MCU→PC | `CAPS` | `isr_freq(f32) max_pts_per_dec(u8) reserved(u8) max_vec_len(u16) default_amp(f32) fw_ver(4B)` | **结构体 4 字节对齐**（见 3.7），共 16 B payload；连接后自动读，校验上位机配置 |
| `0x03` | PC→MCU | `SET_CONFIG` | `freq_start(f32) freq_step(f32) amplitude(f32) vec_len(u16) cycles_mode(u8) mode(u8) reserved(u8)` | 共 17 B（无填充）。原表 12 B 算错（3×4+2+1=15）；补 `reserved` 后 17 B，逐字段序列化，长度不必是 4 的倍数。固件按 17 B 校验。`mode`：0=Plant（开环）1=LoopGain（闭环）。**一次扫频一种模式** |
| `0x04` | PC→MCU | `START` | — | 启动扫频 |
| `0x05` | PC→MCU | `ABORT` | — | 停止回 IDLE，**注入立即归零** |
| `0x06` | PC→MCU | `GET_STATUS` | — | 轮询进度 |
| `0x86` | MCU→PC | `STATUS` | `state(u8) flags(u8) freq_index(u16) pass(u8) reserved(u8) cur_f_act(f32)` | 共 10 B（无填充）。`flags`：bit0=占空比饱和, bit1=ADC饱和, bit2=注入已关, bit3=done；`pass`：单 pass 后**固定为 0**（保留字段，见 3.4） |
| `0x07` | PC→MCU | `GET_DATA` | `start_idx(u16) count(u8)` | 请求一段结果 |
| `0x87` | MCU→PC | `DATA` | `start_idx(u16) count(u8) then count×{f_act, a_c, a_s, b_c, b_s}` | **每点 5×f32 = 20 B**；一帧最多 7 点（3+140=143 B，留裕量）。PLANT：b=X(in) 累加器；LOOP：b=Inj 累加器 |
| `0x08` | PC→MCU | `SET_COEFF` | `order(u8) b[0..3](f32)` | 下发补偿器系数 |
| `0x88` | MCU→PC | `COEFF` | `order(u8) b[0..3](f32)` | 系数回读校验 |
| `0x09` | PC→MCU | `GET_COEFF` | — | 读回 MCU 中**当前生效**的补偿器系数 |
| `0x88` | MCU→PC | `COEFF` | `order(u8) b[0..3](f32)` | `SET_COEFF` 的回显，或 `GET_COEFF` 的应答（**同一帧格式**） |
| `0x0A` | PC→MCU | `GET_CONDITIONS` | — | 读 Vin/Vout/Iout/开关频率 |
| `0x8A` | MCU→PC | `CONDITIONS` | `vin, vout, iout, fs, deadtime, temp, adc_fs_v, shunt_gain` 各 f32 | 8×4 = 32 B，无填充；存进 meta.json（pu 标定系数，D15） |

**v2 删除**：`SET_AMP_LIVE`（扫频中改幅值毁 GH 数据一致性，00 文档 D8）；CL 通道及 `mode_mask`。

**v4 新增 `GET_COEFF`（0x09）的理由**：v3 只有 `SET_COEFF`，它的 `COEFF` 回显
只能证明"**刚写进去的**是什么"，不能证明"**现在生效的**是什么"——
如果两次下发之间 MCU 被复位、或用户手动改了系数，上位机无从知晓。
读回的值要填回 Tab2 输入框，这是"界面显示"与"固件实际"对账的唯一手段。
实现要求：`GET_COEFF` 的应答直接读**当前生效的系数结构体**，不要缓存上一次
`SET_COEFF` 的入参——那样等于自己回显自己，读回无意义。
未实现 `sfra_proto_get_coeff()` 的固件（弱符号默认返回 -1）回 `NACK BAD_PARAM`，
上位机据此把「读回」按钮置灰并说明原因，而不是静默失败。

**PC 端对 DATA 的解释（相位约定唯一实现处，=`model/bode_data.py`）**：
```
PLANT: H  = (a_c − j·a_s) / (b_c − j·b_s)              # Y / U
LOOP : GH = (a_c − j·a_s) / ((b_c−a_c) + j·(a_s−b_s))  # Y / (Inj − Y)
```
LOOP 式推导：$Z_{inj} - Z_y = (b_c - a_c) - j(b_s - a_s)$，分子分母同乘 $-1$ 后即上式括号里的 `(b_c−a_c) + j(a_s−b_s)`。**写成这个形式是为了让代码只做一次复数除法**，不要在中途手工取负号。

**错误码**

| 码 | 含义 | 上位机动作 |
|---|---|---|
| 0x01 | CRC 错 | 重发（重试 3 次） |
| 0x02 | 参数非法（f > Fs/5、amplitude 越界） | 弹窗提示，不重试 |
| 0x03 | 状态机忙 | 等待后重试 |
| 0x04 | 未配置 | 自动先发 `SET_CONFIG` |
| 0x05 | 索引越界 | 改请求范围 |
| 0x06 | 扫频中禁止的操作（如 SET_CONFIG） | 先 ABORT |

## 3.4 时序

**连接**：
```
PING → PING_ACK（验波特率） → GET_CAPS → CAPS（填 UI、校验 isr_freq） → GET_CONDITIONS → CONDITIONS
```

**扫频（边扫边出图）**：
```
SET_CONFIG → ACK
START → ACK
loop every 200 ms:
    GET_STATUS → STATUS（freq_index 递增）
    已完成的点数涨了 → GET_DATA(start_idx, 7) 一次拉一段，
        PC 实时算 mag/phase → 图表生长
STATUS.flags.done=1 → GET_DATA 补齐漏点
```

> **轮询周期必须 < 400 ms，默认 200 ms。**
> 固件 `SFRA_PROTO_TIMEOUT_MS = 500`：MCU 连续 500 ms 收不到任何有效帧就自动 ABORT。
> 200 ms 给一次 USB 枚举抖动留了 2.5 倍裕量；400 ms 已在断线边缘。

> **LOOP 模式也是单 pass（D19），`pass` 字段恒为 0。**
> 旧版这里写过"LOOP 下 `freq_index` 会停留两倍长的时间（pass 0→1）"，
> 那是 D19 之前"两 pass 分别采 Y 和 Inj"的旧设计，已作废。
> 现在 `inject()` 在同一周期同时累加 Inj、`monitor()` 累加 Y，
> 所以 `GET_DATA` 能拿到的点数 = `freq_index`，进度条按 `freq_index / vec_len` 显示即可，
> **不要再乘 2 或除 2**。
> `STATUS.pass` 字段保留是为了协议向前兼容（固定填 0），上位机不得据此分支。

- 超时：单命令 500 ms 重发，累计 3 次断开提示。
- 断点续传：PC 记住最大连续 idx（`LinkController._next_idx`），重连后只拉剩余（数据仍在 MCU 数组）。
  **只接受 `chunk.start_idx == 期望 idx` 的段**——否则频率序列会出现重复或倒序，
  Bode 曲线的横轴就不再单调，PM/GM 会算出垃圾。**断点续传只在同一模式内有效**，换模式必须重扫。
- **MCU 端 500 ms 无任何有效帧 → 自动 ABORT**（安全护栏，不依赖上位机）。ABORT 后留下的半张表 PC 端标记为"不完整"，不允许算 PM/GM。

## 3.5 MCU 侧实现要点

1. `sfra_proto_poll()` 状态机：`WAIT_HEAD1 → HEAD2 → LEN → CMD → PAYLOAD → CRC`，每次调用限量处理，绝不阻塞。
2. UART 中断只做"字节进 ring buffer"，**不在 ISR 解析协议**。
3. `DATA` 帧整帧一次 `uart_write`（或 DMA）；TX 空间不足标记 pending 下次重试，**不发半帧**。
4. `ABORT` 与通信超时都必须**立即**置 `amplitude=0`、清 `dtft_running`。
5. float 拆字节用 `memcpy`，不用 union 指针强转（strict-aliasing 未定义行为）。
6. `f_act` 必须由固件算好写入 freq 数组再上报（D7），PC 不反推。
7. **payload 里不要直接 `memcpy` 整个 C 结构体**：编译器会按 4 字节插填充（例如 `u8 + f32` 之间会补 3 字节）。协议表里的字段顺序**已按"宽字段在前、窄字段靠后"排好且显式留了 `reserved`**，逐字段序列化。

## 3.6 三处容易踩的协议细节

| 坑 | 表现 | 规避 |
|---|---|---|
| **结构体填充** | PC 解出来的 `vec_len` 是垃圾值 | 逐字段序列化 + 测试里断言每个 payload 字节数（`test_protocol.py` 已列为用例） |
| **CRC 范围** | 偶发误判错帧 | CRC 从 `LEN` 开始算到 payload 末字节，**不含 0xAA 0x55**；初值 0xFFFF，多项式 0xA001（反射），结果高地位按 LSB-first 发出 |
| **帧同步丢失** | 上电后第一帧必错一次 | 收帧状态机在 `WAIT_HEAD1` 收到非 0xAA 时**原地等待**（不重入），`HEAD2` 收到非 0x55 时**回到 HEAD1 且把当前字节当新 HEAD1 再判一次**——否则 `AA AA 55` 这种序列会漏掉真头 |
| **`GET_DATA` 的 NACK 被吞（坑 A18）** | 日志报 `mcu拒绝0x07：INDEX_RANGE`，进度条冻结不动，界面永不收尾 | 见下方专段 |
| **`freq_index` 被当成"已完成数"** | 边界请求稳定吃 `INDEX_RANGE`；DONE 后尾点永远拉不完 | 见下方专段 |

### 3.6.1 `STATUS.freq_index` 与固件 `avail` 必须逐字对齐（坑 A18）

固件 `do_get_data()` 的越界判据是：

```c
avail = (state == SFRA_ST_DONE) ? cfg.vec_length : point_idx;
if (start >= avail) { send_ack(p, SFRA_CMD_GET_DATA, SFRA_ERR_INDEX, 0u); return; }
```

而 `STATUS.freq_index` 报的就是 `point_idx`，含义是**"正在采集的索引"**，不是"已完成点数"。两边语义必须严格对齐，否则会踩两个反向的坑：

| 场景 | 错误写法 | 后果 |
|---|---|---|
| 非 DONE | `_available = freq_index`，然后从 `_available - 1` 开始请求 | 起点恰好等于 `avail`，**稳定吃一次 `INDEX_RANGE`** |
| DONE | `_available = min(freq_index, n_total)` | DONE 后 `point_idx` 停住不再涨，但 `avail` 已是 `vec_length`，**最后一批点永远拉不完** |

正确做法（`LinkController._on_status` 现行实现）：

```python
if st.done:
    self._available = int(self._n_total)          # 对齐 avail = vec_length
else:
    self._available = min(int(st.freq_index), self._n_total)
```

非 DONE 时可读区间是 `[0, point_idx)`，共 `point_idx` 点；请求起点必须 `start < point_idx`。按上式算 `want = _available - _next_idx` 就天然不会越界。

**更要紧的是 NACK 不能静默丢弃。** `GET_DATA` 不在上位机 `_pending_acks` 队列里（那个队列只排 `SET_CONFIG`/`START`），所以它的 NACK 走到 `_on_ack` 末尾的 `if not self._pending_acks: return` 时会被吞掉。此时 `_fetching` 停在非零值，而 `_on_poll()` 第一句就是 `if self._fetching > 0: return` —— 上位机再也不发 `STATUS`，扫频彻底停摆，进度冻结在最后一次成功取数的百分比上（实测 57%），而 MCU 那边可能早就 DONE 了。

修法与判据：

- `_on_ack` 里给 `GET_DATA` 单独开分支，**无论什么错误，先无条件清 `_fetching`**（解除轮询封锁）；
- `INDEX_RANGE` 属于正常竞态，记日志 + 计数后重试，**不判扫频失败**；累计超过 200 次才判"两侧点数不一致"并停止；
- 其它错误码才判真失败——同样先清 `_fetching`，保证 `sigDone` 能正常发出，界面不会无限转圈。

守门用例：`test_get_data_nack_releases_fetch_gate`、`test_get_data_hard_error_stops_cleanly`（`src/tests/test_link_controller.py`，`pytest -m e2e`）。

## 3.7 为什么不用 MODBUS / ASCII

| 方案 | 结论 |
|---|---|
| **自定义二进制（采用）** | 快、带 float 原值、可分帧续传、有进度语义 |
| MODBUS RTU | 寄存器模型别扭、float 要拆 2 寄存器、无"进度"语义，不采用 |
| ASCII 文本 | 体积大 3~5 倍、float 精度损失，不采用 |
