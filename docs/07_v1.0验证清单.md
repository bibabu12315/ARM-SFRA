## 2. 上板前必须确认的三件事

### 2.1 烧录后芯片真的在跑

**这一条踩过大坑，务必照做。**

Keil 命令行 `UV4.exe -f xxx.uvprojx` 只做"擦除→编程→校验"，  
**烧完不复位**。芯片会停在 HALTED（PC = 0x20000000，SRAM 起始地址），  
表现是：

- 烧录日志显示 `Verify OK`，看起来一切正常；
- 串口一个字节都收不到，文本 shell 和二进制协议同时失声；
- 很容易误判成"新固件把板子烧坏了"。

**正确做法：用下面这条命令烧录**，它内部会用 pyOCD 补一次复位：

```bat
cd D:\project_code\Python_project\SFRA
.venv\Scripts\python.exe tools\flash_and_run.py
```

输出里必须有这几行：

```
向量表: SP=0x20001D10 Reset=0x080000D5
复位后停在: PC=0x080000D4
运行状态: State.RUNNING
✅ 芯片已进入 RUNNING
```

如果卡在 `State.HALTED`，按一下板上 RESET 键，或拔插 USB 供电。

### 2.2 串口没有被别的程序占用

串口是**独占**的。SecureCRT、串口调试助手、PuTTY  
任何一个是打开状态，上位机就连接不上（会提示"端口可能被其他程序占用"）。

### 2.3 波特率

固定 **921600**。上位机不用手动选，握手时会确认。

## 4. 实时性指标（关键技术验收）

这一节是 v1.0 的**技术核心**，需要串口终端敲命令。  
用 SecureCRT 连 COM14 @ 921600，或在 shell 里直接操作。

### 4.1 ISR 占用

```
msh /> sfra cost
```

如果提示 `not measured`，说明当前固件没开测量（正常，量产构建关着）。  
需要重新打开：把 `SFRA/sfra_local_cfg.h` 里的  
`SFRA_LOCAL_MEASURE_ISR_COST` 改成 1，重编译烧录。

打开后跑一次扫频，再读：

```
sfra cost: avg=1312 max=1475 n=101387 drop=0 budget=7200 cyc (avg=18% max=20%)
  inject: avg=301 max=320 cyc | rest: avg=1011 max=1155 cyc
```

**判据**：

| 指标         | 要求    | 实测      | 结论     |
| ---------- | ----- | ------- | ------ |
| avg 占预算    | < 50% | **18%** | ✅ 余量充足 |
| max 占预算    | < 80% | **20%** | ✅ 抖动小  |
| drop（异常样本） | 0     | **0**   | ✅ 测量可信 |

`budget = HCLK / f_isr = 72 MHz / 10 kHz = 7200` 周期。

### 4.2 溢出计数

```
msh /> sfra
```

看 `ovr=` 这个数：

```
sfra DONE pt=48/49 fs=10000 crc=0 ovr=0 obj=sk2 fc=1000 txt=109 bin=84 orp=0
```

**`ovr=0` 是硬指标**。它统计"ISR 执行时间超过节拍周期"的次数。  
扫频全程必须为 0，否则说明控制节拍被拖垮、数据不可信。

> 历史对比：定点化之前浮点版是 `ovr=78301`（几乎每拍都超时），  
> 定点化之后才是 0。详见 §6。

### 4.3 时间稳定性

```
msh /> uptime
```

连续观察几次，确认数值单调递增、没有跳变或回退。

## 5. 已知限制（不是 bug，是设计边界）

| 限制                  | 原因                                    | 影响                    | 后续                               |
| ------------------- | ------------------------------------- | --------------------- | -------------------------------- |
| 扫频上限 fs/5 = 1930 Hz | 10 kHz 采样率的奈奎斯特约束 + 工程余量              | 看不到 1 kHz 转折点之后完整的高频段 | 提到 100 kHz 可解决                   |
| PM/GM 显示 None       | 被测对象是开环低通，无穿越                         | 分析页部分指标为空             | 接闭环功率级后正常                        |
| LOOP 模式曲线整体 +30 dB  | 软件 DUT 是开环模型，`Y≈Inj`，`Y/(Inj−Y)` 分母趋零 | 看起来像算法坏了              | **S6a 阶段请一律用 PLANT 模式**；接真功率级后正常 |

| Keil 命令行烧录不复位       | Keil 的行为，命令行无等价开关                     | 芯片停在 HALTED，串口无声      | 用 `tools/flash_and_run.py`       |

## 6. 本次 v1.0 修掉的三个真问题

记录在这里，方便将来回归时对照。

### 6.1 烧录后板子"失联"（最耗时的一个）

**现象**：Keil 命令行烧录，`Verify OK`，但串口一个字节都没有。  
文本 shell 和二进制 PING 同时失声。

**误判过**：以为是新固件把板子烧死了、以为是 ISR 测量代码有毒。

**真因**：Keil 命令行 `-f` **不复位芯片**。用 pyOCD 读寄存器：

```
复位前: state=State.HALTED  PC=0x20000000
```

`PC=0x20000000` 是 SRAM 起始地址，说明芯片停在复位后的初始状态，  
根本没执行 Flash 里的代码。向量表本身是对的  
（`SP=0x20001D10 Reset=0x080000D5`）。

**修复**：写 `tools/flash_and_run.py`，在烧录后用 pyOCD  
执行 `reset_and_halt()` → `resume()`。

### 6.2 ISR 占用 96%，控制节拍被拖垮

**现象**：`sfra` 命令输出 `ovr=78301`，几乎每拍都超时。

**测量**：分阶段计时（见 §4.1）

```
总:      avg=6947  max=8148   (预算 7200 → 96% / 113%)
inject:  avg=2204  max=2217
rest:    avg=4743  max=5931
```

**真因**：PY32F071 是 Cortex-M0+，**没有 FPU**。ISR 里所有 float  
运算都是 `__aeabi_fmul` / `__aeabi_fadd` 软件例程。具体：

- `sin_q15` 用 int64 乘法（`__aeabi_lmul`），每拍调 3 次；
- `acc_mac` 每次先 `float × 2^27` 转 Q27，每拍调 4 次；
- `sfra_dut_step` 是浮点 TDF-II，5 乘 4 加；
- `sfra_inject` 每拍做 3 次浮点缩放。

**修复**：开启 `SFRA_USE_FIXED_POINT=1` 并把 ISR 路径彻底定点化  
（详见 §6.3）。结果：

| 指标      | 修复前         | 修复后            |
| ------- | ----------- | -------------- |
| ISR avg | 6947 (96%)  | **1312 (18%)** |
| ISR max | 8148 (113%) | **1475 (20%)** |
| `ovr`   | 78301       | **0**          |
| 幅值精度    | 0.052 dB    | **0.025 dB**   |

精度**同时变好**了，因为定点消除了浮点舍入的累积。

### 6.3 定点化改了哪些地方

| 文件                              | 改动                                                                      |
| ------------------------------- | ----------------------------------------------------------------------- |
| `sfra_core.c` `sin_q15()`       | 去掉 int64 乘法。插值小数点从 22 位降到 16 位（足够），差值右移 1 位防溢出                          |
| `sfra_core.c` `acc_mac()`       | 入参从 float 改成 Q15 整数，去掉 `float×2^27` 转换                                  |
| `sfra_core.c` `sfra_inject()`   | 新增 `amp_q15` 缓存（每频点算一次），ISR 里只剩整数乘 + 移位                                 |
| `sfra_core.c` `sfra_monitor()`  | 定点分支直接用 Q15 输入，跳过 `sfra_sig_to_f()`                                     |
| `sfra_core.c` `sfra_acc_to_f()` | **新增**：累加器 → float 的唯一收口点，两条路径定标不同（Q42 / Q30）不能混                        |
| `sfra_core.h`                   | `sfra_t` 增加 `amp_q15`；`sfra_core.h` 顶部加 `SFRA_LOCAL_USE_FIXED_POINT` 翻译 |
| `sfra_dut.c`                    | 新增 `biquad_q15_t` + `sfra_dut_step_q15()`，系数在 `dut_build()` 里一次性转 Q15   |
| `sfra_pend.c`                   | ISR 的测量分支和常规分支都改用定点调用；测量方法从 `HAL_GetTick()` 改为 SysTick VAL 差值           |
| `sfra_local_cfg.h`              | 新增 `SFRA_LOCAL_USE_FIXED_POINT = 1`                                     |

**另外修掉的测量 bug**：原来的 ISR 计时用  
`ms * (LOAD+1) + (LOAD-VAL)`，`ms` 是开机毫秒数，跑一分钟就  
`60000 × 72000` 溢出 32 位，输出 `max=4294903495`（=0xFFFF0007）。  
改成「SysTick VAL 直接相减 + COUNTFLAG 判重装」，不再依赖 ms 计数。

## 7. 出问题时怎么查

### 7.1 上位机连不上

| 现象              | 检查                                        |
| --------------- | ----------------------------------------- |
| 下拉框只有"假MCU(本机)" | USB-TTL 插好了吗？设备管理器有 COM 口吗？               |
| 提示"端口可能被其他程序占用" | 关掉 SecureCRT / 串口助手                       |
| 握手超时            | 用 `tools/shell_probe.py COM14` 看板子有没有任何输出 |

### 7.2 串口完全没反应

```bat
cd D:\project_code\Python_project\SFRA
.venv\Scripts\python.exe tools\shell_probe.py COM14
```

- **收到东西** → 板子活着，问题在上位机侧
- **什么都没收到** → 跑 `tools\flash_and_run.py --verify-only`，  
  看是不是 `State.HALTED`；是的话复位或重新烧录

### 7.3 扫频结果是平的 / 全 +30 dB

**检查模式**。`sfra` 命令输出里的 `obj=sk2` 表示 PLANT 模式。  
如果上位机选了 LOOP 模式，会看到整条曲线抬高几十 dB、相位乱跳——  
那是**开环模型配 LOOP 模式**的必然结果（见 §5）。

### 7.4 曲线形状对但数值差一个常数倍

检查是否混用了两条数值路径的累加器定标。  
float 路径是 Q42（还原乘 2^-42），Q15 路径是 Q30（还原乘 2^-30），  
差 2^12 = 4096 倍。统一走 `sfra_acc_to_f()` 就不会错。

## 9. 一键验收（推荐用这个代替 §1）

```bat
cd D:\project_code\Python_project\SFRA
.venv\Scripts\python.exe tools\accept.py --port COM14
```

输出：

```
  PASS  上位机单元测试            {'passed': 147, 'failed': 0}
  PASS  界面端到端走查            {'passed': 24, 'failed': 0, 'warn': 0}
  PASS  真板精度校验             {'mag_db': 0.04, 'phase_deg': 0.228}

*** v1.0 验收通过 —— 可以放行 ***
报告已写入：docs\08_验收报告.md
```

常用变体：

| 命令 | 用途 |
| --- | --- |
| `--no-hw` | 没接板子，只跑单元测试 |
| `--only pytest` | 只跑某一项（`pytest` / `walk` / `health`） |
| `--port COM7` | 指定串口 |
| `--no-report` | 不写报告文件 |

**判定规则**（比 §1 更严，防止假绿）：

- 幅值偏差 ≤ 0.5 dB、相位偏差 ≤ 2.0 °；
- 走查必须 `失败 0`；
- **有一项被跳过就不算完整验收**（只报"已跑的 N 项通过"）；
- **解析不到偏差数值也算失败**——之前这里返回通过，
  握手失败、一个数都没测到时反而报 PASS，是很危险的假绿。

### 9.1 这个脚本自己修掉的两个坑

写验收脚本时踩到、并已修好的问题，记下来免得重犯：

**① 父进程探测串口 → 子进程握手超时**

最初 `wait_port_free()` 用 `QSerialPort` 真的 open/close 一下来
"验证可占用"。结果父进程开过一次之后，子进程（走查脚本）再去 open
就握手超时——**稳定复现**（`accept.py` 里 22/2，
单独跑走查 24/0/0）。

改成纯只读检查：只确认端口在枚举列表里 + 等 1.2 s。

**② 跳过项被算成通过**

第一版 `--no-hw` 跑完，三项里两项跳过，却打印
`*** v1.0 验收通过 ***`。现在跳过即不计入通过，
只报"已跑 N 项通过，还不构成完整验收"。
